# Technischer Prüfbericht – 2026-09-06

Dieses Dokument hält Befunde und Änderungen für die weitere Arbeit mit Claude
oder anderen Werkzeugen fest. Es beschreibt den Stand des Branches
`status-abgleich` nach Commit `0efab1a` plus die noch nicht eingecheckten
Änderungen dieser Prüfung.

## Ergebnis

Der Rust-Code war vor den Änderungen kompilierbar; 210 vorhandene Tests,
`rustfmt` und Clippy liefen fehlerfrei. Der CI-Lauf `34017826817` meldete am
selben Tag 0 bekannte RustSec-Schwachstellen. Nach den Änderungen umfasst die
Suite 216 Tests.

Die wiederkehrende macOS-Meldung wurde in den lokalen TCC-Systemlogs eindeutig
identifiziert:

- Dienst: `kTCCServiceSystemPolicyNetworkVolumes`, teilweise zusätzlich
  `kTCCServiceSystemPolicyDownloadsFolder`.
- Fero lief aus `/private/.../AppTranslocation/.../Fero.app`.
- TCC meldete `Failed to match existing code requirement` und verglich
  verschiedene `cdhash`-Werte.
- Viele Zugriffe waren bereits gleichzeitig angefordert, sodass nach dem
  Bestätigen sofort der nächste wartende Dialog erschien.

Damit sind drei Ursachen belegt: Start aus AppTranslocation, eine bei ad-hoc
signierten Builds wechselnde TCC-Codeidentität und parallele Pfadprüfungen.

## Umgesetzte Änderungen

### macOS-Dateizugriffe

- `resolve_data_dir()` merkt sich das Ergebnis für die Prozesslaufzeit. Zuvor
  legte fast jeder API-Aufruf erneut eine Schreibtestdatei an und löschte sie.
- Kurze Zugriffs- und Coverprüfungen laufen durch ein gemeinsames Gate. Eine
  noch unbeantwortete macOS-Freigabe kann dadurch keine Kaskade gleichzeitiger
  Dialoge mehr erzeugen.
- Der Reachability-Cache ist jetzt „single flight“: Der Cache-Lock bleibt bis
  zum Ergebnis der ersten Dateisystemprüfung gehalten.
- Erkennt Fero `AppTranslocation` im eigenen Programmpfad, erscheint dauerhaft
  ein Installationshinweis in der Oberfläche.
- Ein mit `v*` getaggter macOS-Release bricht in der CI ohne Apple-Zertifikat
  ab. Entwicklungsartefakte dürfen weiterhin ad-hoc signiert werden.

Wichtig: Code kann keine stabile Apple-Codeidentität ersetzen. Für Freigaben,
die auch nach einem Update zuverlässig erhalten bleiben, muss der Release mit
Developer ID signiert und notarisiert werden.

### Sicherheit

- Alle bekannten Custom-Protocol-Routen haben nun eine feste HTTP-Methode.
  Schreibende Aktionen und native UI-Aktionen akzeptieren nur `POST`.
- `POST` verlangt `Content-Type: application/json`. Eine fremde Webseite im
  Login-/Cloudflare-Fenster kann dadurch keine Löschung, keinen Import und
  keinen nativen Ordnerdialog über ein einfaches HTML-Formular auslösen.
- Die CSP erlaubt die eigene Herkunft nun ausdrücklich auch in `connect-src`;
  Skripte, Objekte und fremde Frames bleiben gesperrt.
- Der gemeinsame HTTP-Client liest Textantworten höchstens bis 32 MiB und
  Binärantworten höchstens bis 20 MiB. Die Begrenzung greift während des Lesens
  und damit vor der bisherigen nachgelagerten Bildgrößenprüfung.

### Dokumentation

- `README.md` beschreibt Installation, Entwicklung, Release-Signierung und die
  Modulaufteilung.
- Sicherheitsentscheidungen und die Ursache der macOS-Meldung stehen sowohl in
  diesem Bericht als auch direkt an den relevanten Codepfaden.

## Noch offene oder bewusst akzeptierte Punkte

1. **Apple-Signierung/Notarisierung:** Die benötigten Secrets und ein gültiges
   Developer-ID-Zertifikat müssen außerhalb des Repositories eingerichtet
   werden. Ohne sie bleiben Workflow-Artefakte Test-Builds mit wechselndem
   Code-Hash.
2. **Manueller Test mit Netzvolume:** Im Testsystem war kein kontrolliertes NAS
   zum automatisierten Abnahmetest verfügbar. Zu prüfen ist: App nach
   `/Applications` kopieren, einmal erlauben, beenden, erneut starten und danach
   einen neuen signierten Build installieren.
3. **Generische Webnovel-Quellen:** Der generische Adapter darf absichtlich
   beliebige HTTP(S)-Hosts lesen. In einer lokalen Einzelbenutzer-App ist das
   funktional sinnvoll; würde Fero später eine von außen erreichbare API
   erhalten, müssten Loopback-, Link-local- und private Zielnetze gegen SSRF
   gesperrt werden.
4. **Transitive Wartungshinweise:** RustSec meldete 17 „unmaintained“-Hinweise,
   einen „unsound“-Hinweis für `glib 0.18.5` und ein zurückgezogenes
   `chacha20 0.10.1`, aber keine bekannte Schwachstelle. Die GTK/glib-Pakete
   stammen aus dem Linux-Zweig von Tauri; mehrere alte `unic`-Pakete kommen über
   den HTML-Parser. Bei den nächsten Tauri-/`scraper`-Updates erneut auditieren.
5. **CI-Actions:** GitHub weist darauf hin, dass mehrere verwendete Actions noch
   Node 20 deklarieren und derzeit zwangsweise unter Node 24 laufen. Die
   jeweiligen Actions sollten nach Prüfung ihrer aktuellen Major-Versionen
   aktualisiert werden; das ist kein Laufzeitproblem der Fero-App.
6. **Atomare Zustandsdateien:** Mehrere kleine JSON-Dateien werden direkt an ihr
   Ziel geschrieben. Ein Abbruch genau während des Schreibens kann eine Datei
   beschädigen; die Listenansicht überspringt beschädigte Abo-Dateien derzeit.
   Als nächste Robustheitsverbesserung sollten Einstellungen, Manifeste und
   Abos über eine temporäre Datei plus atomarem Umbenennen gespeichert werden.

## Abnahmebefehle

```sh
cargo fmt --all -- --check
cargo test --all-targets --locked
cargo clippy --all-targets --locked -- -D warnings
```

Für einen Release zusätzlich das erzeugte Bundle prüfen:

```sh
codesign --verify --deep --strict --verbose=2 Fero.app
codesign -dv --verbose=4 Fero.app
spctl --assess --type execute --verbose=4 Fero.app
plutil -p Fero.app/Contents/Info.plist
```

In `Info.plist` müssen insbesondere `NSNetworkVolumesUsageDescription` und die
Zweckangaben für Downloads/Dokumente/Schreibtisch enthalten sein.
